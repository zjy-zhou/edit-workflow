# 电商 AI 经营平台开发步骤文档

日期：2026-07-08

状态：研发执行草案

关联文档：

- 需求文档：`docs/design/ecommerce-ai-platform/requirements.md`
- 技术设计：`docs/design/ecommerce-ai-platform/technical-design.md`

## 1. 文档目标

本文档将技术设计拆成可执行的开发步骤，用于排期、分工、评审和验收。

拆解原则：

- 先复用 Dify 已有应用、工作流、生成器、运行日志能力。
- 新增电商业务层，避免改动 Dify 核心语义。
- 每一阶段都要能独立验证，避免堆到最后才联调。
- 后端数据结构先稳定，再做复杂业务体验。
- UI 可以先达到可用闭环，再逐步贴近设计稿细节。

## 2. 前置决策

以下问题会影响开发范围，应在进入对应阶段前确认。

| 编号 | 决策项 | 影响阶段 | 建议默认值 |
| --- | --- | --- | --- |
| D1 | MVP 任务执行是否必须真实调用 Dify 工作流 | 阶段 4、5 | 必须关联 workflow_run，但步骤产物可先做简化提取 |
| D2 | 应用中心“获取”的含义 | 阶段 2 | MVP 先按收藏或复制模板二选一，不能只做假状态 |
| D3 | 场景中心附件是否参与生成 | 阶段 3 | 若后端未消费附件，MVP 隐藏附件或标注待支持 |
| D4 | 能力中心、经营增长是否展示 | 阶段 1 | MVP 隐藏，避免空页面 |
| D5 | 商品数据是复用还是任务快照 | 阶段 6 | MVP 支持复用商品记录，同时任务保存输入快照 |
| D6 | 任务产物可见范围 | 阶段 6、7 | MVP 按工作空间权限可见 |

## 3. 总体开发顺序

建议按以下顺序推进：

1. 阶段 0：工程准备与边界确认。
2. 阶段 1：导航、品牌和路由骨架。
3. 阶段 2：应用中心改造。
4. 阶段 3：场景中心接入 Dify 工作流生成器。
5. 阶段 4：电商任务后端表、模型、API。
6. 阶段 5：任务中心前端接真实 API。
7. 阶段 6：任务详情、SOP 步骤、工作流运行关联。
8. 阶段 7：商品、竞品、产物和报告。
9. 阶段 8：权限、安全、观测、回滚。
10. 阶段 9：测试、视觉验收和发布准备。

## 4. 阶段 0：工程准备与边界确认

### 任务 0.1：确认 Dify 二开边界

优先级：P0

问题或价值：

- 避免把 YY Demo 当成可直接粘贴的实现。
- 明确哪些模块复用 Dify，哪些模块新增电商层。

范围：

- 复核现有 Dify 应用列表、工作流编辑器、工作流生成器、运行日志入口。
- 明确 MVP 不重写工作流画布。
- 明确新增代码目录与命名规则。

非目标：

- 不实现业务功能。
- 不新增数据库表。

实现要点：

- 前端新增业务组件放在 `web/app/components/ecommerce/*`。
- 后端新增业务模块放在 `api/controllers/console/ecommerce/*`、`api/services/ecommerce_*`、`api/models/ecommerce.py`。
- 文档中引用的路径必须与实际仓库路径一致。

验收标准：

- 研发团队认可复用边界。
- 后续 issue 不再要求复制 HTML Demo。
- 对外说明清楚：Dify 核心能力保留，电商层增量实现。

验证方式：

- 代码评审前检查新增目录结构。
- 检查是否出现大段 HTML Demo 复制进 React 组件。

### 任务 0.2：建立开发分支和基础检查命令

优先级：P0

问题或价值：

- 统一验证入口，减少后续“能跑但不可测”的问题。

范围：

- 确认前端 lint、typecheck、test 命令。
- 确认后端测试和迁移命令。
- 记录本地启动方式。

非目标：

- 不修复无关历史测试。

实现要点：

- 优先查看根目录 `package.json`、`web/package.json`、`Makefile`。
- 若测试成本过高，先定义每阶段最小验证命令。

验收标准：

- 文档或任务说明中写清楚开发者如何启动和验证。
- 每个阶段都有明确验证命令或人工验收项。

验证方式：

- 至少跑通前端类型检查或相关单测。
- 后端迁移阶段至少跑迁移生成和回滚冒烟。

## 5. 阶段 1：导航、品牌和路由骨架

### 任务 1.1：新增电商主导航入口

优先级：P0

问题或价值：

- 用户需要从主导航进入“我的任务”“应用中心”“场景中心”。

范围：

- 修改 `web/app/components/main-nav/routes.ts`。
- 增加 `/tasks`、`/scene-center` 路由配置。
- 增加中文文案到 `web/i18n/zh-Hans/common.json`。
- 保留 `/apps` 到 Dify 应用中心。

非目标：

- 不实现任务中心和场景中心完整业务。
- 不移除所有 Dify 原有路由，除非产品明确要求。

实现要点：

- `tasks` active 规则匹配 `/tasks` 和 `/tasks/{taskId}`。
- `scene-center` active 规则匹配 `/scene-center`。
- 能力中心、经营增长在没有真实内容前不进入主导航。

验收标准：

- 登录后可从导航看到“我的任务”“应用中心”“场景中心”。
- 点击“我的任务”进入 `/tasks` 占位页。
- 点击“场景中心”进入 `/scene-center` 占位页。
- `/apps` 仍可访问。

验证方式：

- 前端单测覆盖 route visibility。
- 浏览器人工验证导航高亮。

### 任务 1.2：创建任务中心和场景中心页面骨架

优先级：P0

问题或价值：

- 为后续页面开发提供稳定路由。

范围：

- 新增 `web/app/(commonLayout)/tasks/page.tsx`。
- 新增 `web/app/(commonLayout)/tasks/[taskId]/page.tsx`。
- 新增 `web/app/(commonLayout)/scene-center/page.tsx`。
- 新增基础空状态组件。

非目标：

- 不接真实 API。
- 不实现完整设计稿视觉。

实现要点：

- 页面骨架使用现有 Dify 布局和 Tailwind 约定。
- 空状态文案不描述未实现功能过多细节。
- 后续组件放入 `web/app/components/ecommerce/*`。

验收标准：

- 三个路由均可打开。
- 页面无运行时报错。
- 空状态不遮挡导航和账号区域。

验证方式：

- 前端路由 smoke test。
- Playwright 截图检查桌面宽度。

## 6. 阶段 2：应用中心改造

### 任务 2.1：梳理现有应用列表数据流

优先级：P0

问题或价值：

- 应用中心必须复用 Dify app 数据，不应另造一套应用列表。

范围：

- 阅读并标记 `web/app/components/apps/list.tsx`。
- 确认 `consoleQuery.apps.get`、`normalizeAppPagination`、`useAppsQueryState` 的可复用方式。
- 确认现有创建弹窗和权限入口。

非目标：

- 不改 UI。

实现要点：

- 形成改造说明：是包装现有组件，还是新增 `EcommerceAppCenter` 复用数据 hook。
- 如视觉差异较大，倾向新增 `EcommerceAppCenter`，但不要复制 service 逻辑。

验收标准：

- 团队确认应用中心改造方式。
- 不新增重复 app list API。

验证方式：

- PR 中说明复用的 hook 和 service。

### 任务 2.2：实现电商应用卡片和筛选区

优先级：P1

问题或价值：

- 应用中心需要贴近设计稿，突出电商行业分类和场景应用。

范围：

- 应用卡片展示应用图标、名称、描述、标签、创建人或来源。
- 筛选区支持全部、我创建的、我收藏的。
- 搜索框保留现有搜索能力。
- 分类标签包含市场洞察、商品运营、内容创作、付费推广、新品开发。

非目标：

- 不实现推荐模板后端。
- 不改变 Dify app 的核心字段。

实现要点：

- 收藏可先复用 Dify starred apps。
- “获取”语义未定时，不上线假按钮；可先使用“打开”或“复制”。
- 保持分页或无限加载。

验收标准：

- 现有应用可以以新卡片展示。
- 搜索、筛选、打开应用正常。
- 无权限用户看不到创建操作。

验证方式：

- 应用列表组件测试。
- 桌面和移动端截图。
- 手动打开 workflow app 确认进入 Dify 工作流编辑器。

## 7. 阶段 3：场景中心接入工作流生成器

### 任务 3.1：实现场景中心输入与快捷标签

优先级：P0

问题或价值：

- 用户需要通过一句话创建电商场景。

范围：

- 场景中心输入框。
- 快捷标签：市场洞察、商品运营、内容创作、付费推广、新品开发。
- 基础输入校验。
- 空状态和错误状态。

非目标：

- 不做真实附件生成，除非后端已支持。
- 不做复杂画布预览。

实现要点：

- 输入最大长度与 Dify generator 后端限制保持一致或更保守。
- 点击快捷标签只填充或追加提示词，不直接发起生成。
- 未实现附件消费前隐藏附件上传入口。

验收标准：

- 空提示词不能提交。
- 用户点击快捷标签后输入框内容变化。
- 提交后进入生成中状态。

验证方式：

- 组件单测覆盖输入校验。
- 人工验证快捷标签。

### 任务 3.2：接入 `generateWorkflowStream`

优先级：P0

问题或价值：

- 复用 Dify 已有自然语言生成工作流能力。

范围：

- 调用 `web/service/debug.ts` 中的 `generateWorkflowStream`。
- 处理 plan、result、error、completed 回调。
- 展示生成计划和最终结果状态。
- 支持取消或防重复提交。

非目标：

- 不修改后端 generator 算法。
- 不新增生成接口。

实现要点：

- 使用已有 `GenerateWorkflowBody` 类型。
- 默认 mode 可先用 `workflow`，若需要自动判断再用 `auto`。
- 后端返回错误时保留用户输入。

验收标准：

- 正常返回 result 时能拿到 graph。
- plan 阶段能展示生成进度。
- 失败时有可读错误信息。
- 多次点击不会并发创建多个生成请求。

验证方式：

- mock SSE 单测。
- 人工使用一个简单 prompt 生成工作流。

### 任务 3.3：发布生成结果为 Dify 工作流应用

优先级：P0

问题或价值：

- 场景生成必须形成可编辑、可运行的 Dify 应用。

范围：

- 复用或抽取 `applyToNewApp`。
- 创建 app 后同步 graph 到 draft。
- 发布成功后跳转 `/app/{appId}/workflow`。
- 同步失败时复用回滚策略。

非目标：

- 不自动发布到外部市场。
- 不改 Dify app 创建接口。

实现要点：

- app 名称优先使用 generator 返回的 `app_name`。
- 描述可使用用户 prompt 截断。
- 图同步失败要展示错误，不吞掉 orphan app 信息。

验收标准：

- 生成结果可以创建为 Dify app。
- 创建后打开工作流编辑器能看到生成节点。
- 同步失败不会静默留下不可理解的空应用。

验证方式：

- E2E：输入 prompt -> 生成 -> 创建应用 -> 打开 workflow studio。
- 单测覆盖 apply 失败分支。

## 8. 阶段 4：电商任务后端表、模型、API

### 任务 4.1：新增电商数据模型和迁移

优先级：P0

问题或价值：

- 任务、步骤、商品、竞品、产物必须持久化。

范围：

- 新增 `api/models/ecommerce.py`。
- 新增迁移文件。
- 表包括：
  - `ecommerce_task_types`
  - `ecommerce_tasks`
  - `ecommerce_task_steps`
  - `ecommerce_products`
  - `ecommerce_competitors`
  - `ecommerce_task_artifacts`

非目标：

- 不修改 Dify `apps`、`workflows`、`workflow_runs` 表结构。
- 不实现复杂数据连接器。

实现要点：

- 所有主业务表包含 `tenant_id` 或可通过父记录追溯 tenant。
- 任务表保存 `app_id`、`workflow_id`、`workflow_run_id` 引用。
- step 表保存 step 快照，避免任务类型变更影响历史任务。
- artifact 不存超大内容，必要时只存文件引用和元数据。

验收标准：

- 迁移可升级。
- 迁移可回滚。
- 模型字段与技术设计一致。
- 不影响现有 Dify 表。

验证方式：

- 后端迁移测试。
- 数据库约束检查。

### 任务 4.2：种子任务类型

优先级：P0

问题或价值：

- 任务创建需要初始类型和 SOP。

范围：

- 初始化“搜索主图策划”。
- 初始化“商机发现”。
- 写入 sop_schema。

非目标：

- 不做完整任务类型管理后台。

实现要点：

- 使用稳定 code：
  - `search_main_image_planning`
  - `opportunity_discovery`
- 系统内置任务类型 `tenant_id` 可为空，或按平台现有模式处理。
- 重复执行 seed 不应产生重复记录。

验收标准：

- 新环境启动后可查询到两个任务类型。
- 重复迁移或 seed 不产生重复 code。

验证方式：

- 后端测试查询 task-types。

### 任务 4.3：实现任务类型与任务 CRUD API

优先级：P0

问题或价值：

- 前端任务中心需要真实数据。

范围：

- `GET /console/api/ecommerce/task-types`
- `GET /console/api/ecommerce/tasks`
- `POST /console/api/ecommerce/tasks`
- `GET /console/api/ecommerce/tasks/{task_id}`
- `PATCH /console/api/ecommerce/tasks/{task_id}`

非目标：

- 不实现任务运行。
- 不实现商品、竞品和产物完整流程。

实现要点：

- 所有查询过滤 `tenant_id`。
- 创建任务时根据 task_type 初始化 steps。
- 列表支持分页、状态、任务类型、关键词。
- 详情返回 task、product、steps、artifacts 基础结构。

验收标准：

- 用户可创建任务。
- 列表可查到任务。
- 详情可查到任务及步骤。
- 越权访问返回 403 或 404，不泄露数据。

验证方式：

- 后端 API 单测。
- tenant 隔离测试。

## 9. 阶段 5：任务中心前端接真实 API

### 任务 5.1：实现任务 service 和类型定义

优先级：P0

问题或价值：

- 前端任务中心需要稳定数据契约。

范围：

- 新增 `web/service/ecommerce-tasks.ts`。
- 新增 `web/types/ecommerce-task.ts`。
- 封装列表、详情、创建、更新接口。

非目标：

- 不在组件里直接拼接复杂 fetch 逻辑。

实现要点：

- 类型字段与后端响应对齐。
- 列表请求支持 page、limit、status、task_type_id、keyword。
- 错误处理遵循现有 service 约定。

验收标准：

- 任务组件可以通过 service 获取数据。
- 类型检查通过。

验证方式：

- TypeScript typecheck。
- service mock 单测。

### 任务 5.2：任务列表页

优先级：P0

问题或价值：

- 用户需要浏览、搜索和筛选任务。

范围：

- `/tasks` 页面。
- 页签：全部、未完成、已完成。
- 搜索。
- 任务类型筛选。
- 任务卡片。
- 空状态、加载态、错误态。

非目标：

- 不展示复杂报告内容。
- 不运行任务。

实现要点：

- 未完成可映射 `draft`、`running`、`waiting_for_input`、`failed`。
- 已完成映射 `succeeded`。
- 卡片点击跳转 `/tasks/{taskId}`。

验收标准：

- 用户可看到任务列表。
- 搜索和筛选生效。
- 空列表有合理提示。
- 分页或加载更多可用。

验证方式：

- 组件测试。
- 浏览器人工验证。

### 任务 5.3：创建任务弹窗

优先级：P0

问题或价值：

- 用户需要从任务类型创建任务。

范围：

- 任务名称。
- 任务描述。
- 任务类型选择。
- 创建成功刷新列表并进入详情或停留列表。

非目标：

实现要点：

- 任务类型从 API 获取。

- 描述长度限制与后端一致。

验收标准：

- 创建成功后数据持久化。
- 刷新页面任务仍存在。
- 表单校验错误可见。

验证方式：

- 表单单测。
- E2E 创建任务。

## 10. 阶段 6：任务详情、SOP 和工作流运行关联

### 任务 6.1：任务详情基础页

优先级：P0

问题或价值：

- 用户需要查看任务上下文、步骤和状态。

范围：

- `/tasks/{taskId}`。
- 任务标题、描述、状态。
- SOP 步骤列表。
- 当前步骤。
- 基础操作按钮。

非目标：

- 不做沉浸式报告模式。
- 不做复杂右侧 AI 对话。

实现要点：

- step 顺序使用后端返回 order。
- 任务类型变化不影响历史任务步骤展示。
- 404、无权限、加载失败有明确状态。

验收标准：

- 任务详情可打开。
- 步骤状态展示准确。
- 刷新后状态一致。

验证方式：

- 详情页组件测试。
- 通过 API 创建任务后人工验证。

### 任务 6.2：任务运行 API

优先级：P0

问题或价值：

- 任务需要关联真实 Dify workflow_run，才能追踪执行。

范围：

- `POST /console/api/ecommerce/tasks/{task_id}/run`
- `POST /console/api/ecommerce/tasks/{task_id}/stop`
- 运行后保存 `workflow_run_id`。
- 更新任务和步骤状态。

非目标：

- 不实现所有复杂 step-output 映射。
- 不实现外部电商数据工具。

实现要点：

- 校验任务 task_type 是否有关联 app 或 workflow。
- 构造 Dify workflow inputs。
- 运行失败时任务进入 `failed`。
- 停止运行时任务进入 `stopped`。

验收标准：

- 运行任务后任务状态变为 `running`。
- 有 workflow_run_id。
- 失败时错误可见。
- 停止运行可更新状态。

验证方式：

- 后端运行 API 单测。
- 与一个测试 workflow app 做联调。

### 任务 6.3：任务详情展示运行状态和日志入口

优先级：P1

问题或价值：

- 用户需要知道任务是否还在运行，并能排查失败。

范围：

- 任务详情显示运行中、失败、成功。
- 提供 Dify workflow run log 链接。
- 支持手动刷新或轻量轮询。

非目标：

- 不复制完整 Dify log UI。

实现要点：

- 链接使用 app_id 和 workflow_run_id 组合。
- 无 app_id 或 run_id 时隐藏日志入口。
- 轮询间隔要保守，避免压垮后端。

验收标准：

- 运行状态可更新。
- 失败任务可看到错误摘要。
- 点击日志入口可到 Dify 日志或详情页。

验证方式：

- E2E 运行任务并查看状态变化。
- 手动模拟失败状态。

## 11. 阶段 7：商品、竞品、产物和报告

### 任务 7.1：商品创建和选择

优先级：P1

问题或价值：

- 任务执行需要商品上下文。

范围：

- `POST /console/api/ecommerce/products`
- `GET /console/api/ecommerce/products`
- 任务详情选择或创建商品。
- 保存商品到任务。

非目标：

- 不做复杂商品库管理。

实现要点：

- 商品支持名称、描述、平台、类目、图片文件 ID。
- 文件上传复用 Dify 已有上传能力。
- 任务保存 product_id，并在 inputs 中保留快照。

验收标准：

- 可创建商品。
- 可将商品关联到任务。
- 刷新后商品仍显示。

验证方式：

- 后端 API 测试。
- 前端表单测试。

### 任务 7.2：竞品候选和确认

优先级：P1

问题或价值：

- 商机发现和主图策划需要用户确认竞品。

范围：

- 保存竞品候选。
- 支持用户选择或取消选择。
- 任务详情展示竞品列表。

非目标：

- 不实现真实竞品抓取。
- 不接第三方电商平台。

实现要点：

- 竞品数据可由工作流输出或手动录入。
- selected 字段表示用户确认结果。
- 竞品归属 task，避免跨任务误用。

验收标准：

- 可以展示候选竞品。
- 用户选择后状态持久化。
- 后续步骤能读取选中竞品。

验证方式：

- 前端交互测试。

### 任务 7.3：产物和报告展示

问题或价值：

范围：

- `GET /console/api/ecommerce/tasks/{task_id}/artifacts`
- 产物卡片。
- 报告详情。
- 支持 report、strategy_card、image、table、file、text、link 基础展示。

非目标：

## 12. 阶段 8：权限、安全、观测和回滚

### 任务 8.1：统一权限校验

优先级：P0

问题或价值：

- 防止跨工作空间或越权访问任务、商品、产物。

范围：

- 后端所有 ecommerce API 校验 tenant。
- 创建、编辑、运行、查看分别校验权限。
- 前端根据权限隐藏操作。

非目标：

- 不新增复杂 RBAC 后台。

实现要点：

- MVP 优先复用 Dify 当前工作空间权限。
- 服务端是最终权限边界，前端隐藏只是体验优化。
- 任务详情无权限时不泄露任务是否存在。

验收标准：

- A 工作空间用户无法访问 B 工作空间任务。
- 无创建权限用户无法创建任务或场景应用。
- 无运行权限用户无法运行任务。

验证方式：

- 后端权限测试。
- 前端权限 mock 测试。

### 任务 8.2：安全边界检查

优先级：P0

问题或价值：

- 商品外链、文件、raw_data、模型输入都可能带来风险。

范围：

- 文件 ID tenant 校验。
- raw_data 默认不返回。
- 外链导入不上线或走安全抓取层。
- 任务产物内容做基础长度与类型限制。

非目标：

- 不实现完整 DLP。

实现要点：

- 任何 file_id 入参都检查归属。
- 不将 provider secret 或内部错误堆栈写入 artifact。
- 模型提示词中使用附件内容前必须有明确数据处理策略。

验收标准：

- 非法 file_id 被拒绝。
- API 响应不包含未授权 raw_data。
- 外部 URL 不会被后端直接任意访问。

验证方式：

- 安全单测。
- 手动构造越权 file_id。

### 任务 8.3：状态流转日志和回滚方案

优先级：P1

问题或价值：

- 任务运行失败后需要可排查，发布失败后需要可回滚。

范围：

- 记录任务状态变化。
- 记录 workflow_run_id。
- 文档化回滚策略。
- 发布前检查新增迁移是否可回滚。

非目标：

- 不接完整 APM 平台。

实现要点：

- 日志至少包含 task_id、tenant_id、old_status、new_status、workflow_run_id。
- 回滚不删除 Dify apps/workflows/runs。
- 删除 ecommerce 表前需确认生产数据保留策略。

验收标准：

- 后端日志能追踪任务状态变化。
- 发布文档包含回滚步骤。

验证方式：

- 触发任务运行成功和失败，检查日志。
- 迁移回滚演练。

## 16. 最小可演示闭环

如果需要尽快做一个内部演示，建议最小闭环如下：

1. 用户进入平台后看到“我的任务”“应用中心”“场景中心”。
2. 用户进入场景中心，输入“生成一个搜索主图策划工作流”。
3. 系统调用 Dify generator 返回 workflow graph。
4. 用户点击发布，系统创建 Dify workflow app 并进入工作流编辑器。
5. 用户进入我的任务，创建“搜索主图策划”任务。
6. 用户打开任务详情，看到 3 个 SOP 步骤。
7. 用户点击运行任务，任务保存 workflow_run_id 并展示运行状态。

这个闭环不要求真实竞品抓取和图片生成，但必须真实创建 Dify app、真实持久化任务、真实保存 workflow_run_id。
